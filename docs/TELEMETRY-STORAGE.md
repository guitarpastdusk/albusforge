# M6b — Partitioned raw readings, rollups and retention

This builds on the merged standalone ingestion service (PR #32). The implementation on `m6/telemetry-storage` adds PostgreSQL-native daily partitions, durable rollup work markers, SQL aggregation and owner-run storage maintenance. No external application, queue service or cloud resource is introduced by this application PR. Terraform and scheduler/job provisioning remain with Claude albusforge-44.

## Data path

1. Cloudlink commits a packet's raw readings, receipt, latest values, status and usage as before. An `AFTER INSERT` statement trigger adds one `dirty_hours` marker per affected device/channel/hour in the same transaction. Failed ingestion cannot leave orphan work markers.
2. `telemetry-rollup` claims the oldest marker with `FOR UPDATE SKIP LOCKED`. It replaces that hour's minute/hour aggregates from raw SQL results, then deletes the marker and commits. Concurrent workers claim different markers. If ingestion waits on a claimed marker, its upsert recreates or updates it after the worker commits; late data is not silently lost.
3. `telemetry-maintain` creates partitions, advances the accepted raw-data boundary and expires data only where no dirty marker remains. A failed or delayed rollup defers deletion rather than discarding unaggregated readings.

Each rollup stores count, numeric sum, min, max, deterministic last value and population standard deviation. Latest sample ordering is timestamp, sequence, then ordinal, matching ingestion. Aggregates are replaced rather than incrementally added, so replaying a job does not double count. Sum and standard deviation use PostgreSQL `numeric` arithmetic; callers can derive mean with SQL `sum / n`. Models do not calculate these values.

## Partitions and upgrade

Migration `0002_telemetry_rollups.sql` and its snapshot are generated by drizzle-kit. `0003_telemetry_partitions.sql` is a journaled drizzle-kit custom migration because native partitioning and transition-table triggers are not represented in the schema DSL. The schema drift check still covers the modeled columns, constraints and indexes.

The upgrade attaches the existing readings table as `readings_default`, preserving its rows, and creates the partitioned parent. It queues preexisting readings for aggregation and creates today's partition plus seven future UTC days. The raw primary key now includes `ts`, as required for a partitioned unique constraint; packet receipts remain the cross-partition retry authority. No public wire-format change is needed.

The default partition accepts dates whose daily partition does not yet exist, including historical backfill or a missed scheduler run. Maintenance drains its retained dates into daily tables and attaches them under a lock, without losing dirty markers. Queries through `telemetry.readings` see default and daily data together. Ingest must write through the parent table so its statement trigger runs; direct writes to child tables are not a supported application path.

The native partition operations follow the [PostgreSQL 16 partitioning rules](https://www.postgresql.org/docs/16/ddl-partitioning.html); transition-table handling follows [CREATE TRIGGER](https://www.postgresql.org/docs/16/sql-createtrigger.html). This is not an online, lock-free conversion. Upgrade and partition maintenance acquire table locks; validate lock durations on representative data and schedule the initial conversion appropriately before fleet rollout.

## Retention rules

- Raw: retain at least 90 days, with the cutoff rounded down to a UTC day. Drop daily partitions ending at or before the cutoff only after their dirty markers are gone. Expired default-partition rows are likewise deleted only after aggregation.
- Minute rollups: retain at least seven days, rounded down to a UTC day. Late samples older than that still update hourly history but do not recreate expired minute buckets.
- Hourly rollups: retained indefinitely while the owning device exists. Existing tenant/device cascade deletion behavior is unchanged.
- Receipts and usage: unchanged; receipts are not pruned. A receipt TTL still requires a separate replay policy.
- Latest values: unchanged; they remain available for offline-device displays after raw expiry.

Maintenance records a monotonic `retention_state.raw_before` watermark while holding the raw parent lock. The insert trigger rejects samples behind that watermark. Cloudlink maps that constraint failure to `422 timestamp_out_of_range`, rolling back the entire packet. This prevents an expired late sample from causing an incomplete recomputation that overwrites a previously complete hourly aggregate. Replaying a committed receipt remains valid because it inserts no raw samples.

Deletion can deliberately lag its target if aggregation falls behind. Monitor that backlog; do not override the guard to save space. A failed transaction rolls back partition movement, watermark changes and deletion together.

## Job contract for infra

The existing `db-jobs` image gains two entrypoint tasks:

| Job/task | Suggested schedule | Database role | Behavior |
| --- | --- | --- | --- |
| `telemetry-rollup` | Every minute | `albus_app` | Processes up to `TELEMETRY_ROLLUP_LIMIT` dirty hours (default 64, allowed 1–1024), oldest enqueued first; multiple instances safely divide work |
| `telemetry-maintain` | Daily, e.g. 00:05 UTC | `albus_migrate` / table owner | Creates ahead/backfill partitions and expires eligible data; advisory lock serializes maintenance |

Both use direct PostgreSQL with existing `DB_HOST`, `DB_PORT`, `DB_NAME`, `DB_USER`, `DB_PASSWORD`, `DB_SSL=require` in Cloud Run. Each job uses a one-connection pool, 5s connection timeout, 300s statement timeout and 301s client query timeout. Maintenance has a 2s lock-acquisition timeout and fails safely for retry rather than waiting indefinitely. DDL after lock acquisition can still delay HTTP writes; firmware must buffer/retry transient failures. Account for each concurrent job's connection in the production budget.

The ingest role cannot execute the partition-creation function or perform table DDL. No `SECURITY DEFINER` escalation is used. Cloudlink never runs maintenance at startup. The owner job uses its own configured credential; do not grant DDL rights to the service role. The migration runner's owner default privileges cover partitions created later by that same owner.

Local commands, after migrations and using a development DB:

```sh
# Standard DB_* environment; use the application role.
pnpm --filter @albusforge/db telemetry:rollup
# Switch DB_USER/DB_PASSWORD to the local table owner for DDL.
pnpm --filter @albusforge/db telemetry:maintain
```

Container commands are `db-jobs telemetry-rollup` and `db-jobs telemetry-maintain`, or select the same task through `CLOUD_RUN_JOB`. The tasks log counts or a generic failure and exit; they never log credentials or raw readings. Re-running either task is safe. Infra owns schedules, retries and rollout; no jobs are created or dispatched by this PR.

## Validation and rollout gates

Tests exercise fresh migrations and an upgrade with preexisting unpartitioned readings, native routing, numeric aggregates and ties, late data, concurrent workers, failed aggregate writes, a marker-delete/ingest race, fallback-partition drainage, raw-retention deferral, retained hourly history, expired backfill rejection, and restricted app-role permissions. Existing cloudlink integration tests run on the new schema.

Before production: review the custom DDL, deploy the migration and job images in order, provision schedules, verify private-network/TLS connectivity and role grants, and load-test migrations/maintenance and concurrent ingestion. Observe oldest dirty-marker age, queue depth, fallback-partition row count, maintenance failures, database connections/CPU/I/O and HTTP latency/503s. Tune job batch limits and parallelism to the same measured Cloud SQL budget as cloudlink; do not assume the defaults prove fleet capacity.

Next application work: durable events and tenant-scoped dashboard queries/SSE, followed by deterministic detectors and model narration. Production provisioning/token lifecycle and hardware-to-cloud acceptance remain separate gates.
