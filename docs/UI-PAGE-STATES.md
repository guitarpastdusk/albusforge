# Page loading and recovery states

Projects (list and detail), Usage and device telemetry have their own lightweight loading and error boundaries. Project/device detail also have opaque not-found states with links back to their authorized lists. These use the installed Next App Router conventions: `loading.tsx`, client `error.tsx` with **retry()**, and `not-found.tsx` reached by the existing `notFound()` calls. The existing fleet loading boundary remains unchanged.

Each state has one main landmark, an h1, readable narrow-screen copy and navigation away from the pending or failed page. Loading descriptions use a live status and contain no protected project/device/usage data; they do not take focus while users navigate. Error boundaries focus their recovery heading when mounted and expose a keyboard-accessible Try again button that calls Next's retry to refetch/re-render the segment. Error messages and stacks are never rendered; only the diagnostic digest is shown. Error copy allows for changed access as well as service failure rather than asserting every failure is a temporary outage.

Authorization remains next to page data access. No 401/403 is converted into an empty page or a not-found result. A failed session lookup retains the sign-in redirect; a later data authorization failure continues to the error boundary. An inaccessible project/device that the gateway intentionally represents as 404 receives the same not-found copy as an absent resource. Page states make no additional API requests or changes to session transport, no-store behavior or tenant scoping.

Usage and the project list have no item-specific not-found contract, so they receive loading/recovery states without unused not-found files. Errors from shared ancestor layouts remain covered by existing outer boundaries. Once streaming has sent headers, Next can retain HTTP 200 while rendering a not-found or error state, or performing a late in-stream session redirect. The UI preserves not-found/noindex and authorization behavior; the gateway response remains authoritative for access status, so the outer streamed HTML status alone does not establish successful access. Project and device pages have descriptive static document titles for route announcements without exposing private names in metadata.

Validation: all 624 web tests, typecheck, lint and production build pass. Ten new DOM/component tests check the loading landmarks/live statuses, opaque missing-resource navigation, error focus, redaction and retry invocation. Actual Chrome exercised the built app at 320px and 1440px with isolated HTTP schema fixtures: delayed loading becomes content; all four page types recover from 503 after keyboard Tab/Enter activation of Try again; both detail pages show their 404 states; Usage 403 remains an error and /me 401 redirects to sign-in. Error views have no horizontal page overflow and no hydration mismatch was observed. Evidence is in `/tmp/albusforge-page-state-browser/results.json` and sibling screenshots/scripts on the development machine. Fixture checks are not deployed gateway/database or real-account acceptance evidence.
